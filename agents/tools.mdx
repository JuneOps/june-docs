Tools are the actions June can take in the Agent, in runbooks and in access policies. Each tool belongs to a provider, such as Okta or Jamf, and is either a **Read** tool that looks something up or a **Write** tool that changes something. You can also build custom tools for your own HTTP APIs. For when a tool needs approval, see [When June acts without asking](/agents/agent#when-june-acts-without-asking).

Find them under **Settings** > **Agent** > **Tools**.

**Who can do this:** Admin and Owner see the catalog, manage credentials and build custom tools (**Create & manage custom Tools**). Setting which roles can use a tool needs **Manage roles & permissions**, which Owner has by default.

## Browse the catalog

Tools are grouped by provider. A provider that isn't connected shows a **Connect** button, and its tools appear dimmed because June skips them. If the action you need isn't in the catalog, you can [build a custom tool](#build-a-custom-tool).

## Control which roles can use a tool

There's no global switch for a tool. You allow or block each one for each role.

**Who can do this:** Owner (**Manage roles & permissions**).

<Steps>
  <Step title="Open the role">
    Go to **Settings** > **Roles**, open a role, and select the **Tools** tab.
  </Step>
  <Step title="Choose Allow or Block">
    Set each tool to its default, **Allow** or **Block**. Each row says why a tool is allowed or blocked. A tool that returns recovery keys or PINs is **Restricted** and can't be allowed for someone who lacks permission to see that information.
  </Step>
  <Step title="Save the role">
    Save to apply. Removed access applies even in open chats, and new access reaches new chats.
  </Step>
</Steps>

Defaults:

- Integration tools are on for Admin and Owner and off for other roles.
- June's own tools follow the role's permissions. For example, assigning an asset needs permission to update assets.
- A custom tool with no permissions chosen is for Admin and Owner only.

To turn a tool off for everyone, block it on every role, or disconnect the integration. See [Members and roles](/admin/roles).

## Employee self-service

A tool marked **Available for self-service** can run in a runbook an employee triggers with their own request, and it acts only on the requester. Filter for these with **Availability** > **Self-service**. Employee Request runbooks can use only these tools, up to 20 tools and 12 actions per request.

## Credentials

Credentials let custom tools authenticate to your APIs. Open **Settings** > **Agent** > **Credentials** and click **Add credential**. Owners and Admins can add, edit and delete anyone's credentials, including ones a teammate created.

<Steps>
  <Step title="Name it">
    Give it a name and an optional description.
  </Step>
  <Step title="Pick the auth method">
    Choose bearer token, API key, basic auth, OAuth 2.0 (client credentials) or none for a public API. Each asks for its own fields.
  </Step>
  <Step title="Enter the secret">
    Secrets are stored encrypted and never shown again. When editing, leave the field blank to keep the current one.
  </Step>
  <Step title="Add allowed hosts">
    List every host the credential may call, up to 20. Requests go over https to those hosts only.
  </Step>
</Steps>

To delete a credential that a tool uses, first choose another authentication method for that tool.

## Build a custom tool

<Steps>
  <Step title="Start">
    Click **Create tool** and give it a name and description.
  </Step>
  <Step title="Choose authentication">
    Pick a connected June integration or a stored credential, or add a credential securely.
  </Step>
  <Step title="Tell June when to use it">
    Write **Agent guidance** that says when June should use the tool. It is required to publish.
  </Step>
  <Step title="Define inputs">
    Add an input for each value the tool needs, with a name, type and description.
  </Step>
  <Step title="Add API requests">
    Set the method, an https URL and the rest of each request. A tool can chain up to 10 requests, and later ones can use values captured from earlier ones. Secrets can only come from the credential, never from headers or inputs. A tool is a Write tool if any request uses a method other than GET.
  </Step>
  <Step title="Choose what is returned">
    Rename returned values, or hide ones only needed by later requests.
  </Step>
  <Step title="Set availability">
    Turn on **Self-service** if employee runbooks may use it. Set **Software access** to **Grant access** or **Revoke access** to use it as a step in an [access policy](/agents/access-policies).
  </Step>
  <Step title="Set team access">
    Choose the permissions people need. With none, only Admin and Owner can use it.
  </Step>
  <Step title="Test, save, publish">
    Run **Test draft**. Each request can be **Live** or **Mock**, and a live request that writes asks you to confirm because June doesn't retry or roll back test requests. Then save the draft and publish.
  </Step>
</Steps>

A custom tool is always in one of four states:

- **Draft**: saved, not available to June.
- **Published**: the version June uses. It may also have **Draft changes** not yet published.
- **Inactive**: June can't use it. Publish the saved draft to bring it back.
- **Archived**: removed from pickers, and June can't run it. You can't archive a tool that a runbook or access policy still uses.

Open a tool, then **Tool actions** to **Deactivate** or **Archive** it.

In a Personal Agent chat you can also ask June to draft a custom tool. When you ask, it publishes or deactivates one without an approval card, and it never live-tests from chat.

## If something looks wrong

<AccordionGroup>
  <Accordion title="A Member can't use an Okta tool">
    Integration tools default to Admin and Owner. Allow the tool for the role under **Settings** > **Roles** > **Tools**.
  </Accordion>
  <Accordion title="A provider is greyed out">
    The integration isn't connected. Click **Connect** and finish its setup.
  </Accordion>
  <Accordion title="I can't publish a custom tool">
    It needs a description, **Agent guidance**, at least one request, and a label and description on every input.
  </Accordion>
</AccordionGroup>

## FAQ

<AccordionGroup>
  <Accordion title="Is my API secret sent to the AI model?">
    No. Credentials are never shared with the AI model. Secrets are stored encrypted, and requests go only to the hosts you list.
  </Accordion>
  <Accordion title="Can a custom tool grant app access?">
    Yes. Set **Software access** and choose it as a grant or revoke step in an access policy.
  </Accordion>
</AccordionGroup>
